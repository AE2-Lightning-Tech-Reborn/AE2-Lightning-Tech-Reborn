# 无线过载控制器能源与频率卡供电设计

状态：设计阶段，尚未实现。更新日期：2026-10-12。目标仓库：AE2-Lightning-Tech-Reborn。当前代码参考 Minecraft 1.21.1、NeoForge 分支，其他版本需要单独适配。

在无线过载控制器上整合运行期间的 ME 供能代理与无线 FE 供电。过载频率卡沿用已有频率绑定操作，同时支持登记普通用电机器。自动绑定新增小额真实输入探测，降低误接能量垃圾桶后抽空网络储能的风险。

无线终端等设备的同维度与跨维度覆盖另见[网络无线覆盖设计](../无线过载控制器网络覆盖/设计方案.md)。网络覆盖与本方案的 FE 供能、机器无线供电分开设计；覆盖功能的两级划分不改变本文尚待确定的能源功能分级。

## 范围与设计方向

- 只处理已经运行的 ME 网络。普通 AE 储能不足时，通过同一次扣电调用提取 Applied Flux 的 FE 补足差额，避免先断电再补电。
- 完全断电后的冷启动不在范围内，不为此增加本地 FE 盘槽、启动电池或离线读取驱动器的机制。
- 当前方案以高级无线过载控制器承载功能，沿用频率卡只能绑定高级控制器的既有规则。是否下放到普通无线过载控制器待定。
- 同一张频率卡用于 AE 无线联网与机器无线供电，普通 FE 机器不需要安装额外接收方块。
- 仅自动绑定采用保守准入：最多真实输入 100 FE，等目标执行过一次机器 tick 后再观察储量增量，通过前不启用持续供电。手动绑定和已绑定设备的日常运行不做这项探测。
- 当前交付仅为设计文档；界面布局、正式数值和兼容细节仍须在实现时确认。

## 玩家操作

1. Shift 加右键高级无线过载控制器，将其频率写入过载频率卡。
2. 手持已绑定的卡右键目标，登记相应连接；能源连接使用玩家点击的机器输入面。
3. 开启卡片现有的自动连接功能时，放置受支持机器可触发自动绑定与能源准入检查。
4. 绑定由服务端保存，卡片拿走后连接继续工作。再次对已绑定目标操作时，沿用清晰的解除绑定语义；兼具两类能力的目标应统一反馈当前连接状态。

| 目标能力 | 绑定效果 |
| --- | --- |
| 只有 AE 网络节点 | 沿用现有无线网络连接 |
| 只有受支持的电力输入接口 | 登记无线能源接收点，从控制器所在网络取得 FE |
| 同时具有 AE 节点和独立用电接口 | 可一次绑定两项功能，联网与供电分别记录状态 |

能源探测未通过只影响自动供电准入，不因此撤销原本合法的 AE 网络连接。手动选择供电目标按正常绑定流程处理，不要求探测或额外确认；自动跳过的机器也可以直接手动绑定。

建议控制器界面提供“网络 FE 兜底”和“无线供电”两个开关，设备列表显示绑定面、供电状态及实际速率。默认开关值、限流入口和最终界面布局待定，卡片不增加多套难以区分的工作模式。

## 能源来源与分工

无线外供从控制器所在 ME 网络的 Applied Flux FE 库存扣取，网络运行代理将其中的 FE 按 AE2 配置转换为 AE。两条路径分别计量，不能将普通 AE 电池或控制器被动产生的 AE 反向当作网络 FE 发给机器。

建议控制器提供常规无线供电，过载供应器保留插盘缓存与过载供能职责。控制器不因接入共用供电引擎而自动启用供应器的过载行为；这个产品分工仍作为实现建议保留。

同一 ME 网络中的多个控制器共享运行兜底结算与外供预算，不能为同一份 FE 重复预留或重复记账。频率负责目标归属和访问权限，不为每个频率复制一份网络储能。不同网络保持各自的储能归属，不因控制器或频率配置相似而相互借电。

本功能管理的外供应先留出网络运行所需额度，再分配给机器，避免外供在 ME 扣电前取走全部 FE。预留量的计算方式、突发负载余量和与其他模组 FE 出口的协调仍待验证；这不构成对所有外部消费者的全局保电承诺。真实能源耗尽时仍按 AE2 原规则断电。

## 运行期间的供能代理

每次请求电力时按以下顺序处理：

1. 优先调用 AE2 原有供电逻辑，使用普通电源及 AE 储能。
2. 计算本次实际未满足的 AE 差额。
3. 从当前网络提取可用 FE，按目标 AE2 版本的转换比例换算，只补足差额。
4. 将正常供电与 FE 补足部分合并返回，随后由原调用方判断是否缺电。

补足必须发生在同一次请求返回之前，尤其是网络维护扣电判定之前。不能依靠下一 tick 补电，也不能把整个网络的 FE 虚报成每个控制器各自持有的 AE 容量。

模拟扣电同时模拟 FE 的可提取量，但不实际扣 FE、不修改换算余量；正式扣电以真实提取量为准。遵守 AE2 的消耗倍率与单位转换，避免重复应用倍率。整数 FE 与小数 AE 之间的余量应被正确保留和归属，网络拆分、合并、控制器移除时不得复制或丢失已结算能量。

FE 提取使用受控的存储访问路径，不能为了提取 FE 再递归调用同一套用电代理。需要重入保护，并处理存储回调导致的网络状态变化。接入点可评估原生供能服务与能源请求处的有限补充逻辑，具体选择尚未定稿。

## 无线能源接收点

普通 FE 目标登记为能源接收点，不创建虚假的 AE 节点或 `GridConnection`，不占用 AE 频道，也不因能源绑定变化触发频道重算。保留现有 AE 连接路径，另行维护能源接收点集合。

接收点至少记录频率、维度、位置、输入面、目标身份、绑定来源、能源准入状态与探测预算使用情况。目标清单属于服务端频率管理，不塞入卡片中，也不要求给第三方机器直接写入自定义 NBT。

沿用频率访问权限与服务端交互校验。绑定面通过目标模组的电力能力接收能源，遵守侧面设置和原生接收限制。仅查询当前可用的已加载目标；区块卸载暂停供电并保留绑定，重载恢复时重新确认目标和能力。

方块被拆除或替换后，旧能源绑定失效，新目标需要重新绑定。仅当新绑定来自自动放置流程时进行能源探测，手动绑定不探测。替换为同类型方块时仍需要识别实例变化；实现须明确放置代次或等效身份的维护方式。

能源能力失效时立即丢弃缓存，重新解析后确认接口是否仍可用。已经完成绑定的目标不因缓存失效、输入面设置变化或区块重载再次进行能源探测。AE 联网与 FE 供电同时存在时，需识别回灌本网络的接收器，避免循环扣取。该检查不能扩大为禁止所有同网、但具有独立 FE 消耗的机器。

## 自动绑定的小额探测

探测只在尝试建立自动能源绑定时发生，判断目标是否具有可观察的储能行为，不尝试对所有模组的“垃圾桶”作绝对识别。只进行模拟接收无法区分正常机器与无限销毁能源的目标，因此自动准入包含一次有上限的真实输入。手动绑定、已绑定设备运行和普通供电重试均不进入此流程。

### 已核对实现与时序选择

核对范围为 Minecraft 1.21/1.21.1 NeoForge 的本地 JAR，并与对应上游源码对照；这是接口和代码路径核对，尚未进行游戏内整合验收。

| 模组与核对版本 | 能源实现 | 对探测时序的影响 |
| --- | --- | --- |
| Trash Cans 1.1.1、1.0.18c 的能源垃圾桶与终极垃圾桶 | 能源接口返回接收量，但 `getEnergyStored()` 恒为零，没有先入缓存再清空的过程 | 0 tick 已能跳过；等待一个 tick 后同样没有增量 |
| JustDynaThings 1.20.7.1 的 `justdynathings:blackhole` 黑洞 | 对外暴露 JDT 的普通 `MachineEnergyStorage`，先真实存入 FE；销毁启用时在 `tickServer()` 中调用 `extractFEWhenPossible()` | 0 tick 会看到储量增加而放行；默认销毁速率下，执行一次机器 tick 就会清空试送电量 |
| JustDireThings 1.5.7 普通储能机器、JDTE 0.6.1.0 的普通机器储能辅助类与高级能源传输器缓存 | 使用普通 `MachineEnergyStorage`，输入立即增加储量；后续工作或外送可以消耗这些 FE | 能否通过延迟检查取决于这一次 tick 后是否仍有增量，不能把未通过一概认定为垃圾桶 |

因此采用已确认的“一次目标机器 tick 后判定”方案，不采用单独的 0 tick 准入。JDT 的基础能源传输器使用同步分配和聚合储量，也不能假定所有传输器都只报告本地缓存；储量必须来自同一可比较接口。

黑洞默认 FE 容量和每 tick 销毁上限均为 `Integer.MAX_VALUE`。其保留内容配置与红石控制可以关闭销毁，此时它能够作为正常储能使用；配置也允许降低每 tick 销毁量。因此一次 tick 探测只覆盖当前实际运行状态，不能保证识别关闭销毁、低速销毁或之后才切换状态的黑洞。

上游证据：[黑洞 tick 与储能接口](https://github.com/DevDyna/JustDynaThings/blob/443052c574ff984b36407d342cee2672f8814400/src/main/java/com/devdyna/justdynathings/registry/builders/black_hole/BlackHoleBE.java)、[黑洞默认配置](https://github.com/DevDyna/JustDynaThings/blob/443052c574ff984b36407d342cee2672f8814400/src/main/java/com/devdyna/justdynathings/config/ServerConfig.java)、[Trash Cans 能源接口](https://github.com/SuperMartijn642/TrashCans/blob/1fd94ec777713ce885b9af2cf1f5de61d814349a/src/main/java/com/supermartijn642/trashcans/TrashCanResourceHandlers.java)、[JDT 普通储能类](https://github.com/Direwolf20-MC/JustDireThings/blob/506416a9c7675cacc246a47d2b0c9d6b27eff9a8/src/main/java/com/direwolf20/justdirethings/common/capabilities/MachineEnergyStorage.java)。上游链接用于说明对应实现，本地版本结论以已核对 JAR 为准。

### 探测顺序

1. 校验目标、频率权限、绑定面、区块状态和同次放置的历史探测记录。目标必须处于可以执行机器 tick 的范围；仅区块已加载还不够。
2. 查询输入前的储量 `E0`。查询结果必须具有明确单位；无法可靠读取时暂不自动绑定，不先试送电。
3. 模拟该面可接受的电量，将本次真实发送量限制在可接受量、网络可分配 FE 和剩余探测预算之内，总上限为 100 FE。
4. 从真实网络 FE 库存取得探测用电，再通过目标原生接口输入。记录实际接收量 `A`，未被接收的部分返回来源；退回暂时失败时保留可恢复余量，不销毁。
5. 若 `A > 0`，将候选标记为等待观察，暂不登记为可供电的已绑定目标。等待目标执行过一次机器 tick，在目标维度的方块实体 tick 阶段之后读取储量 `E1`。
6. 根据实际接收量与延迟后的储量变化决定是否建立能源绑定。等待期间不再试送电，也不发送常规批量供电；`A = 0` 时直接结束本次尝试。

“等待一次 tick”是游戏逻辑顺序要求，不能用墙钟等待 50 ms，也不能只在下一服务端 tick 开头读取。实现须保证读数发生在输入之后的目标机器 tick 之后，并验证放置事件早于、晚于方块实体 tick 两种顺序。等待期间若目标被替换、卸载或观测接口失效，本次自动绑定结束为未验证，不根据旧读数通过，也不追加试送电。

这里的“查询储量”是只读操作，不调用抽取接口把能源取回来。只允许输入、不允许抽出的正常机器也应能够通过检查。

### 判定结果

| 观测结果 | 自动绑定行为 |
| --- | --- |
| `A > 0` 且目标运行一次 tick 后 `E1 > E0`，两次读数有效且可比较 | 通过本次能源准入，建立绑定并允许持续供电 |
| `A > 0` 但目标运行一次 tick 后 `E1 <= E0` | 跳过自动绑定，记录未观察到保留的储能增量 |
| `A = 0`，包括满电、输入面关闭、网络暂时无可分配 FE | 保留为未通过状态，不认定为垃圾桶，不启动持续供电 |
| 储量不可读、精度不足、发生饱和、前后数据不可比较或观察被中断 | 标记无法验证，不建立自动能源绑定 |

判断使用储量增量，而不是“输入后是否为零”。目标原来已有少量电、却持续销毁新输入时，绝对储量非零不能作为通过依据。读数被限制在整数上限、导致小额输入不可见时，也不能据此认定目标在吞电。

### 探测预算与重试

同一次放置只允许一次自动真实探测，最多输入 100 FE；即使目标只接受其中一部分，也不自动追加第二轮。重复放置事件处理、多个频率卡候选、多个控制器、不同侧面探测、能力通知和区块重载不能把这个上限分别再执行一遍。

服务端保存已探测状态、实际使用额度和结果，正常存档重载后不重新试送电。重启前尚未完成的观察按未验证结束，不将其当作通过。机器更换后若重新触发自动绑定，才按新放置实例处理；自动路径不因计时器到期、持续无储量或缓存失效而反复扣费。手动绑定直接走正常流程，不重开一轮探测。持久化顺序与异常中断恢复需要在实现中验证。

已满电、接口暂不可用或网络无 FE 的目标，何时允许再次进行尚未发生的真实探测，属于待定策略；任何重试都必须受到同次放置总预算和调度预算限制。

### 提示与局限

目标运行一次 tick 后未保留储量增量时，提示：“未检测到储能增加，已跳过自动绑定；可手动绑定。”储量无法可靠读取时使用独立提示，避免把接口不支持查询与真实无增量混为一谈。

即时转发电力的管道、将 FE 转换为其他能源的设备，以及在这一 tick 内消耗了全部探测电量或使储量不高于初值的正常机器，可能被保守筛选跳过。玩家可以直接手动绑定这些目标，不需要通过探测或增加确认步骤；绑定来源记录为手动即可。

该方案覆盖储量恒为零的典型能源垃圾桶，以及已核对的、销毁启用且采用默认速率的 JustDynaThings 黑洞，代价最多为一次 100 FE 的探测。销毁延后多 tick、每 tick 只销毁少量 FE、其他电源同时补入或报告不真实储量的目标仍可能通过。一次探测不提供永久无损保证；已绑定后不继续监控这项储量增量，也不因运行消耗或模式变化追加探测、解除绑定。

## 供电调度与兼容

复用已有无线供电的目标缓存、能力失效监听、按目标反馈调整频率的调度和批量取电。只访问绑定目标与 FE 指定资源，不通过每 tick 扫描全部 ME 库存或世界方块发现设备。常规输送和自动探测均需要有界处理预算，避免大量放置目标在同一 tick 集中执行。

输送遵守实际接收回执，单次拒收后不重复扣除同一份能源。批量预取的 FE、未接收部分与探测余量都要有明确归属，网络切换、拆分、卸载和控制器移除时完成结算或保留恢复状态。

为现有 `TargetAccess` 增加可选的只读储量查询，而不是强迫所有后端都提供伪造的数值。原生 FE、Mekanism、GrandPower、Flux Networks 等后端分别核对单位、精度和可查询能力，不能把“不支持查询”返回成零。

未安装 Applied Flux 时，新增 FE 兜底和无线 FE 供电不可用，已有频率卡联网仍按原规则工作。跨维度供电沿用高级控制器的能力定位，目标维度与区块必须已加载；具体连接数量和供电限额待定。

## 实现前待定项

- 普通无线过载控制器是否获得能源功能，以及高级版与普通版的差异。
- 两个能源开关的默认值和设备列表操作。手动绑定已明确不增加探测或确认流程。
- 网络运行预留量、外供 FE 上限、每 tick 目标数、跨维度限制和公平分配方式。
- 100 FE 探测上限是否做成配置项，以及只读检查未通过时的有限重试条件。
- 多方块电力端口、共享同一储能的多个面、仅提供近似储量的目标如何进行身份与精度判断。
- 运行代理的具体接入点、网络分合后的余量归属和与其他 FE 消费路径的协调。

## 验收场景

1. 正常 AE 电量充足时，代理不额外扣取兜底 FE；电量不足且网络可用 FE 足够时，当次请求补足，运行网络不出现短暂掉电。
2. 模拟请求不改变 FE 库存或换算余量，模拟与正式执行分别遵守各自时刻的实际可用量；倍率变化和小数请求不产生能源。
3. FE 真正耗尽时正常缺电；已完全断电的网络不要求靠本功能重新启动。
4. 频率卡能分别绑定 AE 节点、普通 FE 机器和双能力目标。只绑定能源端点不增加 AE 频道或触发 AE 拓扑变化。
5. 正常储能机器在最多 100 FE 的输入后，执行一次机器 tick 仍保留储量增量时通过；Trash Cans 能源及终极垃圾桶损失不超过本次探测上限，之后不持续供电。
6. JustDynaThings 黑洞在销毁启用、默认速率下，立即读取虽有增量，执行一次机器 tick 后仍必须被跳过；覆盖原储量为零与非零、放置事件在机器 tick 前与后两种时序，等待期间没有常规供电。
7. 正常机器在观察期耗尽探测电量、即时转发或转换设备被自动跳过后，能直接手动绑定；手动路径不探测、不增加确认。满电、不接收、储量未知、读数饱和的目标不被误报为垃圾桶。
8. 重复事件、多侧面、多控制器、区块卸载和正常重载不会重复执行同次放置的真实探测；未绑定目标不会被逐 tick 试送电。观察期中断或重启不得凭旧结果建立绑定。
9. 方块替换不能继承旧供电，同类型替换也重新验证身份；新目标只在自动绑定时探测。已绑定设备的运行、输入面设置变化、能力重建与区块重载都不追加能源探测，且不继续使用过期缓存。
10. 部分接收、退款失败、控制器移除及网络拆分合并都不丢失或复制已提取的 FE；多个控制器不重复结算兜底或预留额度。
11. 本功能外供遵守运行预留与实际输送限制；同网独立用电设备正常工作，明确的本网络回灌路径被阻止。
12. 无 Applied Flux、目标区块未加载、跨维度不可用及频率权限失效时，行为与提示符合对应边界；大量目标绑定和恢复受调度预算约束。
