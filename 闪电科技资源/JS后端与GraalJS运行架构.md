## 1 一份 JS 玩法核心

| 部分 | 权威职责 |
| --- | --- |
| 服务端可信 JS 核心 | 全部内部状态、物质账本、生产与研究公式、动作费用及前置校验、嵌套重置、通讯、结算点数计算、状态序列化与版本迁移 |
| 玩家 JS 脚本 | 读取允许的状态快照，输出购买、分配、重置、通讯和结算意图，以及有限大小的显式 `memory` |
| Java 接入层 | 主线程实际物品与 FE 交接、加载和暂停、逐真实 tick 的外部输入与已批准推进额度、有界后台调度、保存 JS 状态、界面同步、最终点数的范围与身份检查和交付去重 |

Java 不另写科技树、物质转换、升级费用或内部奖励校验。它验证外部交接身份与数量边界，内部经济是否合法由可信 JS 核心判断。Java 保存 JS 生成的序列化载荷及交接元数据，不把内部经济重新建模为另一套 Java 状态。

网页、离线数值仿真和 Minecraft 服务端共用同一个无界面 JS 核心。浏览器负责展示与用户输入，Java 负责世界接入；两者通过同一套快照和动作数据交互。核心不依赖 Vue、DOM、页面计时器、`localStorage` 或系统时钟，也不允许玩家脚本接触持有权威状态的全局对象。

服务端选定的流程脚本属于可信规则，可以定义内容与费用；玩家提交的操控脚本不是规则。即便都使用 JS，也要分别授权、运行和保存。跨 Context 传递有界数据快照，不暴露可变核心对象或允许玩家把代码直接 `eval` 到核心环境。

## 2 一个 t 就是一个真实服务端 tick

在基准 20 TPS 下，一个真实 tick 为 0.05 秒。每个获准推进的真实 tick 对应一个有序帧：核心执行一次推进，每台反应堆的玩家脚本最多调用一次；也可由一次组回调同时安排同一玩家的多台堆。速度倍率只进入公式，不扩大回调次数。

```text
内部推进量 = 本真实 tick 的基准步长 × 已批准速度倍率
加工批量 = min(公式产能、可用原料可支撑量、容量上限)
```

不按内部推进量循环调用完整 tick，不逐个生产天文数量的单位，不逐次购买天文数量的设施。批量购买使用总价公式与有界求解，受材料、前置和数量上限约束。涉及重置或路线改变的动作仍是明确决策，不能未经证明就自动跳过一串重置。

这是直接定义的离散游戏规则，不声称等价于无限细时间步的连续模拟。旧的“沿内部时间寻找所有事件并逐段唤醒脚本”不作为主运行方案；参考实现也应使用相同的冻结帧规则。提高倍率后，一帧中新产出的材料不能立刻被下游链反复消费，若这影响玩法，应调整离散规则或公式，不能偷偷恢复随倍率增长的循环。

### 2.1 帧内顺序

以下为建议的确定性执行顺序；具体动作冲突优先级需在接口规范与测试中固定：

1. Java 在主线程形成同一玩家的加载、暂停、运行集合快照，使用共同的 `N`，实际扣取获准 FE，提交带帧号的推进输入。
2. 玩家脚本读取该帧开始时允许的状态与外部输入，返回有上限的动作列表。回调成功才接纳列表及新的 `memory`；失败时两者都不提交。
3. 可信核心按固定顺序校验动作，在临时状态中预留费用。购买、重置与最终结算的先后不能由方块遍历顺序决定；终结本轮后的旧动作全部失效。具体单个非法动作拒绝还是整批拒绝须由 API 明列。
4. 动作处理后冻结本帧的生产输入与参数，按优先级或明确的分配算法共同分配原料，保留玩家设置的最低余额。各产线不能各自看见同一份可用原料后重复扣费。
5. 汇总生产与通讯结果。新产物及本帧通讯到货到下一帧才可作为加工或转发输入；同一阶段不递归传播。实时支援按本帧开始时的有效关系及有限预算计费。
6. 一次提交核心状态与本帧交接结果，输出必要的界面变化、存档快照和最终结算请求。记录已处理帧号，重复输入不再次扣账或生产。

跨堆来源扣减、接收增加、通讯费和损耗必须共同成功，或共同不发生。并发目标共享来源额度；暂停、卸载和最终结算阻止未完成交付，已经完成的交付不因之后的状态变化回滚。

### 2.2 时间与供电

速度仍按 `sqrt(P / (B × 2^(N - 1)))` 计算，`P` 必须对应实际消耗的能量。Java 负责世界侧扣费与批准量，JS 使用批准输入推进；核心不能根据墙上时钟自行补发免费推进量。

暂停、未加载或离线不接纳新帧、不产生收益。服务器低 TPS、后台积压或限流都会延长现实时间。已经付费接纳的旧帧可以按原有顺序完成，不能被解释为卸载后的新生产。积压帧各有真实帧号与付费依据，按有界批次处理；它们与为了内部加速虚构额外 tick 不同。

3–24 小时目标按实际运行经过时间验收，并记录基准 TPS、供电、脚本和负载条件，不能把内部秒数或压测模拟步数直接当成该目标的证明。

## 3 线程与调度

Minecraft 主线程只操作世界对象、投递不可变输入和接收已经完成的结果，不等待后台 `join`，不直接运行玩家脚本。后台核心不能读取 `Level`、方块实体、背包或 AE 网络对象。

同一玩家的全部反应堆组成顺序调度单元，共享运行集合、通讯顺序与账本交接。不同玩家由有界线程池公平调度，不为每个方块创建线程。一个 Context 同时只由一个线程进入，不并发共享 JS 对象；线程间切换须由宿主串行管理，符合 [GraalJS 多线程模型](https://github.com/oracle/graaljs/blob/master/docs/user/Multithreading.md)。

限制待处理帧、动作、快照、结果、日志和持久 `memory` 的数量及大小。每个调度单元取得有限时间片，先处理旧帧，再接纳新工作；队列满时不能让 MC 主线程代跑模拟。

当积压接近上限时，在世界侧停止接纳新的付费推进，保留已扣 FE、已接纳的帧与收据。不得丢掉付费工作、重复消费同一额度，或在恢复时按经过的现实时间免费追赶。运行集合如何排除被限流的堆须按统一帧边界定义，不能借此回改已经批准的 `N`。

时间片只决定什么时候完成工作，不能改变确定性的成本和产出。脚本语句额度、动作上限属于明确执行规则；负载过高时保护服务器，允许模拟暂时变慢，不承诺无限机器和复杂度下仍满速。

## 4 玩家脚本隔离与恢复

首选继续验证 GraalJS `UNTRUSTED` 隔离模式。核心与玩家脚本使用不同 Context，不同信任域使用不同 Engine；运行单元内可复用编译结果与正常 Context，不在每 tick 新建引擎。使用隔离运行时不等于可以公开宿主对象，仍需关闭 Java 类查找、文件、网络、进程、线程创建与其他非必要能力。依据：[GraalVM 沙箱](https://www.graalvm.org/latest/security-guide/sandboxing/)。

玩家调用采用一次输入快照、一次输出动作列表的粗粒度接口，避免逐个资源反复跨语言查询。限制快照大小、字符串长度、动作总数、输出和日志；核心再次校验所有意图，脚本自称已扣费或已解锁不具有效力。

语句额度约束通常的脚本执行，CPU、堆内存和输出限额作为额外保护。CPU 限额是定期检测的取消机制，不是毫秒精确的调度器；只依赖后台线程或 Java 取消标志不足以替代运行时限制。额度参数应从真实脚本测量确定，本次探针的数值不是生产配置。

超限取消后，原 Context 不再可用，不能下个 tick 从死循环原位置继续。丢弃本次暂存动作和 `memory`，保留最后一次成功提交的显式状态，停止错误脚本并报告原因；修正或明确恢复后新建玩家环境。可信核心状态独立保存，玩家 Context 的关闭不应销毁物质账本。

正常完成一次回调后可以重置适用的执行限额，但不得把重置语句／CPU 计数解释为清除了持续占用的堆内存。还需测试长期存活对象、恶意大字符串、编译峰值及反复重建环境的宿主资源消耗。当前微测试没有证明全部攻击或故障都已被隔离。

## 5 精确数量与持久化

原始物质、通讯数量、费用、结算物质和最终点数采用 `BigInt` 或明确尺度的定点数。含小数的费用、加工与分配使用统一舍入和余量累计；单买与批量买的差异必须来自明文规则，不能来自浮点误差。范围有界、无需精确账本的速率或展示值可以采用近似数。

JSON 与 Java 交接中的精确大整数使用十进制字符串，不能先经 JS `Number` 再转回。临时乘积在足够精度下计算，最后按规则截取到非负 `long` 范围；不得溢出为负数、`NaN` 或无穷。已产结算物质按加工时的工艺价值入账，不在结算时全部乘上当前最高层倍率。

JS 核心快照至少包含规则版本、各堆 `runId`、内部状态、两本永久账、已处理帧号、通讯记录和待交付结算。Java 同时保存接纳但未处理的付费帧、外部交接序号及交付回执，形成同一逻辑检查点，不能只保存其中一边。存档频率和快照复制开销需要压测。

结算点数由 JS 核心计算；Java 只接受当前合法周目与唯一结算序号，检查范围并执行实际资源点交付。输出满时保留待交付量，重试、重启和新轮启动不能重复发奖或覆盖旧收据。世界存档、外部存储提交与回执之间的故障恢复协议仍需在 Minecraft 中实际验证，不能仅凭一次 JS 序列化通过就宣称交付事务已成立。

## 6 现有代码的复用与剩余工作

已有独立 `reactor-model.js` 原样在无浏览器对象的 GraalJS 隔离环境中跑通生产、重置、存档和三子轮自动结算，与 Node 的结果摘要一致。这证明该旧模型可以嵌入，不需要为 Minecraft 重新用 Java 写一遍经济；测试方法与数值见[运行时验证记录](运行时验证记录.md)。

正式核心仍需在 JS 内完成以下改造：

- 分离 TMT 的 Vue、DOM、计时器与浏览器存储；复用可脱离界面的规则，不把整个网页引擎原封不动塞进服务端。
- 替换旧 `advance()` 按 0.25 秒小步循环的方式，建立固定真实帧与批量公式。
- 将旧 `Number` 账本改成精确数量，增加新嵌套重置与收费通讯规则。
- 固定快照／动作协议、版本迁移、限额、线程交接与恢复语义。
- 验证 NeoForge 类加载、Java 运行环境、Windows／Linux／macOS 分发、原生依赖、第三方许可证与多玩家内存成本。

依赖与嵌入方式以实际选定版本的 [Polyglot 嵌入说明](https://www.graalvm.org/latest/reference-manual/embed-languages/) 为准。本次测试坐标不自动成为最终打包方案，也不要求用户为了当前文档安装某种 JDK。
