# 过载相位锁定设计

状态：设计阶段，尚未实现。更新日期：2026-10-27。目标仓库为 AE2-Lightning-Tech-Reborn，现有相位锁定实现参考 Minecraft 1.21.1；具体开发分支与移植版本在实施时确定。

相位锁定分为普通版与过载版。普通版保留现有功能，但不再提供外部传送锁定；过载版包含普通版功能，并提供外部传送锁定与 RNG 定值锁定。RNG 锁定覆盖佩戴者实体自身的随机源，以及可归属到该玩家触发的战利品表计算；世界随机源不锁定。

## 已确认的功能划分

| 功能 | 普通相位锁定 | 过载相位锁定 |
| --- | --- | --- |
| 护甲锁定 | 保留 | 保留 |
| 飞行锁定 | 保留 | 保留 |
| 外力锁定 | 保留 | 保留 |
| 外部传送锁定 | 移除 | 提供 |
| 佩戴者实体自身 RNG 定值 | 不提供 | 提供 |
| 该玩家触发的战利品表 RNG 定值 | 不提供 | 纳入 RNG 锁定范围 |
| 世界随机源锁定 | 不提供 | 不提供 |

“定值”表示随机接口按预先定义的规则返回固定结果。仅固定种子、使随机序列可以重复，不满足此要求。定值也不等于所有概率事件都对玩家有利，实际结果取决于调用方如何使用随机数。

## 玩家实体与战利品表的边界

实体 RNG 锁定作用于佩戴者本身，需要同时覆盖实体内部直接访问随机源和外部通过 `getRandom()` 取得随机源的路径。其他实体自己的随机源不随之锁定。

玩家触发的战利品表即使使用独立的战利品随机源，也属于本功能范围。不能因为战利品计算没有使用玩家实体 RNG，就将其排除。应在本次战利品计算中使用该玩家的定值规则，而不修改被击杀实体的全部随机行为。

以下场景作为归属识别与验收目标，具体入口需要按目标版本核对：

| 场景 | 归属原则 |
| --- | --- |
| 玩家击杀实体产生战利品 | 依据本次击杀与掉落计算的玩家归属，不能把被击杀实体直接当作佩戴者 |
| 玩家破坏方块产生战利品 | 依据本次破坏操作的玩家归属 |
| 玩家钓鱼产生战利品 | 依据钓鱼操作及鱼钩所有者识别玩家 |
| 玩家交互触发容器首次生成战利品 | 依据实际触发生成的玩家；已经生成的物品不重新抽取 |
| 玩家投射物或模组间接行为触发战利品 | 只有能沿明确的责任链识别玩家时才应用；驯服生物、机器与假玩家的具体归属规则待定 |

归属判定不能仅凭附近存在玩家、某玩家装备了模块，或上下文中任意实体字段包含玩家就成立。无法可靠识别触发玩家时保留原有随机行为。多个玩家参与的场景需要明确归属优先级，不能任选一个佩戴者。

同一次战利品计算引用的嵌套战利品表应继承玩家归属与定值规则。战利品条件、抽池和数量等通过该计算上下文随机源进行的抽样应一并覆盖。模组若另建随机源或直接读取世界随机源，须单独核对接入方式，不能宣称已自动覆盖。

## 世界随机源保持原行为

世界随机源、世界共享或命名随机序列不纳入锁定。天气、自然生成、随机刻及无明确玩家归属的环境事件维持原有随机行为。

玩家触发的战利品表原本即使从世界或共享命名序列取得随机源，也应只在本次计算上下文内改用定值规则。不得给共享随机对象重设种子、修改其返回值或回写锁定状态。该计算不得通过共享序列取数来生成定值结果；其他玩家及环境事件继续使用自己的原有路径。

应以战利品计算上下文传递玩家归属，避免使用无隔离的全局“当前锁定玩家”。嵌套调用、异常退出与并发执行后均不能把规则泄漏给其他计算。

## 定值规则的候选方案

具体预设数值、能否由玩家编辑、布尔值与高斯值规则尚未定稿。候选方案是用 `0 ≤ r < 1` 表示统一的定值位置，再按接口返回类型映射：

| 随机接口 | 候选返回规则 |
| --- | --- |
| `nextFloat()`、`nextDouble()` | 返回对应精度的固定值，并保证转换后仍在合法区间内 |
| `nextInt(n)` | 对合法的正整数上界，返回按 `r` 映射的 `floor(r × n)`，保证结果处于 `0` 至 `n−1` |
| 带起点和终点的整数接口 | 按该接口的开闭区间映射，处理溢出与端点 |
| `nextInt()`、`nextLong()` | 单独定义合法的整数预设或映射规则 |
| `nextBoolean()` | 单独定义固定布尔值或明确的映射规则 |
| `nextGaussian()` | 直接返回预设高斯结果，例如 `0`；不依赖固定基础随机值继续进行拒绝采样 |

还需审查 `fork()`、派生随机源和辅助采样方法，防止从锁定范围中绕出，或将锁定传播到无关对象。所有定值映射保留原接口对非法参数的校验。

依赖反复抽样的循环可能在固定返回值下无法结束。随机源内部的采样方法需要直接实现定值结果；调用方自行编写的重试循环需要独立验证与适配。若某路径必须恢复变化的随机值才能运行，应明确标记为兼容例外，不能将其当作严格定值已经成立。

## 安装与配置的建议

建议普通版与过载版作为同类模块互斥安装，由过载版承担完整功能，避免重复安装后出现状态覆盖。护甲、飞行、外力、外部传送与 RNG 锁定分别提供开关；实体 RNG 与玩家触发战利品表共同受 RNG 锁定开关控制。RNG 默认关闭是候选默认值。

外部传送锁定建议沿用现有对玩家主动传送与管理指令的处理规则。普通版即使带有旧存档中的传送锁定配置，也不能继续获得过载版功能；存档迁移方式、是否自动升级旧模块及配方成本尚未确定。

定值配置由服务端校验并执行。停用模块、卸下装备、死亡重生、断线和实体替换后，应清理旧实体的锁定状态。建议在战利品计算入口取得玩家有效状态及定值配置快照，使同一次计算和嵌套表使用一致规则；跨 tick 延迟行为采用哪个时刻的状态，需要在实现时明确。

## 实现验收目标

- 普通版保留护甲、飞行与外力锁定，旧传送配置不能使其越级生效。
- 过载版的传送与 RNG 开关可独立控制，原有主动传送和服务器策略按选定方案保留。
- 同一预设下重复调用各类 RNG 接口得到规定结果，整数边界合法，高斯等采样不死循环。
- 玩家击杀、破坏方块、钓鱼、首次生成容器战利品及嵌套表分别验证归属与定值效果。
- 两名玩家使用不同预设时互不串用；未启用模块、无归属与归属不明的计算保留原行为。
- 玩家战利品使用定值结果时，世界及命名随机序列对象没有被替换、重设种子或挂上锁定状态。
- 停用、死亡重生、重连、异常退出及嵌套调用后无残留锁定。
- 模组自建 RNG、假玩家、间接击杀与拒绝采样循环分别记录验证范围和兼容例外。
